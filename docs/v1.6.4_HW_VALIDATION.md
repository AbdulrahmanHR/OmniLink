# v1.6.4 — On-Hardware Validation Checklist (M29)

Milestone **M29 — Hardware validation & v1.6 hardening [HW]**. This is the
reproducible, **manual** acceptance script a human runs with real ExpressLRS
gear to close the [HW] acceptances that the automated suite cannot reach. It is
developer-facing Markdown and is therefore exempt from i18n.

> **Status of this milestone is HONEST about hardware:** every [HW] path below
> is **code-complete and hardened with mock/pure tests**, but **NONE of the
> on-device acceptances in this document have been executed** — the developer
> has no ExpressLRS TX/RX, no GPS module, and no Backpack. Do **not** mark any
> section PASS unless YOU ran it on real hardware and observed the stated
> result. Fabricated results are worse than an honest `blocked`.

## How to use this document

1. Gather the gear listed under each section's **Preconditions**.
2. Follow the **Steps** exactly, in order.
3. Compare what you see against **Expected**.
4. Tick exactly one box: **PASS** (matched), **FAIL** (did not match — file an
   issue with the captured output), or **blocked** (no gear / could not run).
5. Each section lists the **Code under test** (`file:line`) and the
   **HARDWARE-PENDING markers** it exercises, so a failure can be traced
   straight to the seam.

The automated coverage that backs each path (so you know what is *already*
proven without hardware) is listed under **Already proven (no device)**.

### Conventions

- `TX` = a transmitter module/handset running ExpressLRS; `RX` = a receiver.
- "wire value" = the raw scaled integer on the CRSF bus before the frontend
  applies scaling (see `src/lib/telemetry-crsf.ts`).
- Firmware versions are examples; record the **actual** version you ran.

## (a) GPS readout + live map track — M11 / M13

Confirms a real GPS fix decoded off the CRSF bus reaches the telemetry readout
in human units and drives the live flight-path map.

**Preconditions**

- A TX↔RX ELRS link, bound, telemetry enabled.
- A GPS module wired to the RX (or an FC forwarding GPS over CRSF), with a clear
  sky view so it can acquire a fix.
- OmniLink built from this branch; device connected over USB serial (so the
  `device://link-stats` stream is live).
- Firmware: record TX and RX versions: __________ / __________.

**Steps**

1. Connect the TX over USB; wait for the device card to show target name +
   firmware (CRSF handshake succeeded).
2. Open the Telemetry page. Confirm RSSI/LQ/SNR are updating (link is live).
3. Power the RX + GPS outdoors; wait for satellite count to climb.
4. Watch the **GPS readout**: before a fix it should show "acquiring" (a `0,0`
   reading with a satellite count), and after lock it should show real
   latitude/longitude, altitude in metres, ground speed (km/h), heading (°) and
   satellites.
5. Move the RX/GPS ~50–100 m (walk it) and watch the **map**: a path should
   accumulate following the real track.
6. Note an altitude reading at/near ground and confirm it is plausible (not
   offset by +1000 m, not stuck at 0).

**Expected**

- Pre-fix: readout shows "acquiring", map shows no bogus `(0,0)` marker.
- Post-fix: coordinates match the real location (cross-check against a phone
  GPS); altitude is real metres (`wire − 1000`); the map track follows movement.
- Non-GPS RX (if tested): readout shows no GPS section; link stats still update.

**Code under test**

- `src/lib/telemetry-crsf.ts:102` `gpsFromTelemetry()` (scale/offset), `:121`
  `gpsHasFix()` (0,0 → "acquiring"), `:92` `GPS_ALT_OFFSET_M` (+1000 m bias).
- `src-tauri/src/crsf/mod.rs:504` `decode_gps()` (big-endian 15-byte GPS frame),
  `:381` `Parser::feed()` (framing/CRC/resync).
- `src-tauri/src/commands/device.rs:370` GPS-held-across-tick ingestion, `:522`
  `stats_payload()` (attaches the latest GPS verbatim to each link-stats emit).
- `src/components/telemetry/GpsReadout.tsx`, `src/components/map/PathLayer.tsx`.

**HARDWARE-PENDING markers exercised**

- `src/lib/telemetry-crsf.ts:66` — `CRSF_RF_RATE_HZ` is firmware-dependent and
  UNVERIFIED against a real OTA-rate table; while validating GPS, also record
  whether the reported **packet rate** matches the radio's configured rate.

**Already proven (no device)**

- `tests/unit/telemetryGps.test.ts` — scale/offset, `0,0` preservation, and
  (M29) full ±lat/±lon range + wire-0 → −1000 m altitude.
- `crsf/mod.rs` `#[cfg(test)]` — GPS frame decode + truncated-frame rejection.
- `commands/device.rs` `#[cfg(test)]` (M29) — `stats_payload` attaches GPS
  verbatim and omits it when absent; a GPS frame arriving **before** link-stats
  in a single read tick is held and attached.

**Result:** ☐ PASS  ☐ FAIL  ☐ blocked (no GPS-capable ELRS link)

## (b) Firmware flash incl. Backpack — M8 / M19

Confirms the staged flash pipeline writes real firmware to a real device, the
pre-flash backup is produced, the TX/RX (and TX-Backpack/VRX-Backpack) guards
hold, and a local `.bin` is validated before any write.

**Preconditions**

- A flashable ELRS device (TX or RX) over USB (UART) — and, separately, an
  ExpressLRS **Backpack** (TX-Backpack or VRX-Backpack) reachable over WiFi-OTA.
- A known-good pre-built `firmware.bin` for the connected target (for the
  local-file path).
- **Take a config note first** — flashing rewrites options.
- Firmware to flash: __________.

**Steps**

1. Connect the target over USB; confirm the device card identifies it.
2. Run the wizard to a normal release flash. Watch the staged progress
   (fetch → patch → erase → write → verify → done) and the log.
3. After it completes, confirm a `.elrsp` backup was written to
   `AppData/omnilink/backups/` (timestamped) **before** the write stage ran.
4. **Guard check:** deliberately select an **RX** target while a **TX** is
   connected (or vice-versa). Confirm the flash is **refused** before any erase,
   with a TX/RX-mismatch message.
5. **Local-file path:** pick the known-good `.bin` for the connected target →
   flash. Confirm it validates (size/integrity/target) then writes verbatim.
6. **Local-file mismatch:** pick a `.bin` for the *wrong* class (an RX image
   while a TX is connected). Confirm it is **refused before any write**.
7. **Backpack:** put the Backpack in WiFi mode, select it, flash. Confirm the
   OTA reaches the device's `/update` and the Backpack reboots.
8. **Backpack guard:** select a TX-Backpack image against a VRX-Backpack device
   (or vice-versa). Confirm it is **refused** (cross-type).

**Expected**

- Release flash reaches `done` at 100%; device reboots on new firmware.
- A backup `.elrsp` exists after the flash (and survives a *failed* flash).
- Both guards (TX/RX, TX-Backpack/VRX-Backpack) **block before touching the
  device**; a mismatched local `.bin` is blocked in the fetch stage.
- Backpack OTA succeeds over the same WiFi transport as a plain ELRS device.

**Code under test**

- `src-tauri/src/flash/engine.rs:125` `run_flash()` staged pipeline (guard →
  backup → fetch/validate → patch → upload).
- `src-tauri/src/flash/guard.rs:16` `check_target_compatibility()` (TX/RX);
  `src-tauri/src/flash/backpack.rs:60` `check_backpack_compatibility()`
  (TX-Backpack/VRX-Backpack), `:90` `backpack_firmware()`.
- `src-tauri/src/flash/validate.rs:230` `validate_local_firmware()` (local
  `.bin` gate); `src-tauri/src/flash/patch.rs:57` `patch_binary()` (options
  splice), `:22` `OPTIONS_DELIMITER`.
- `src-tauri/src/flash/msp.rs:95` `enable_passthrough_with_timeout()` (the
  Betaflight-passthrough RX-on-FC path, if you test it).
- `src-tauri/src/flash/backup.rs` `write_backup()`; wizard under
  `src/components/wizard/`.

**HARDWARE-PENDING markers exercised**

- `src-tauri/src/flash/backpack.rs:21-23` and `:78` / `:36` — Backpack firmware
  is a **bundled placeholder** (`PLACEHOLDER_MAGIC`); the real per-target binary
  fetch from `BACKPACK_REPO` (`https://github.com/ExpressLRS/Backpack`) is the
  unimplemented HW seam. When validating, **substitute a real Backpack image**
  for the placeholder and confirm the device accepts it.

**Already proven (no device)**

- `flash/engine.rs` `#[cfg(test)]` — happy path, failure propagation, TX/RX
  guard aborts before upload, backpack skips the options patch, local-file
  validate+verbatim and mismatch-abort; (M29) a **failed upload still leaves the
  recovery backup**, and a **WiFi OTA with no connected-device context allows an
  RX target** (cross-device guard).
- `flash/{guard,backpack,validate,patch,msp}.rs` `#[cfg(test)]` — guards,
  target inference (incl. M29 longest-run + interrupted-header), options-region
  boundaries (incl. M29 exact-fit + one-byte-over), MSP framing (incl. M29
  resync/partial/ack-after-noise).

**Result:** ☐ PASS  ☐ FAIL  ☐ blocked (no flashable device / no Backpack)

## (c) WiFi / Backpack discovery + probe — M18 / M19

Confirms a real ELRS device's self-AP / mDNS broadcast is discovered, correctly
classified (plain ELRS vs Backpack), and that its HTTP identity probe reads back.

**Preconditions**

- An ELRS device in **WiFi mode** broadcasting its self-AP (SSID like
  `ExpressLRS TX` / `ExpressLRS RX`), and/or already joined to the LAN and
  advertising over mDNS.
- An ExpressLRS **Backpack** in WiFi mode (SSID like `ExpressLRS TX Backpack` /
  `ExpressLRS VRX Backpack`).
- A working WiFi adapter on the host (so the platform scan tool runs).

**Steps**

1. Put the ELRS device in WiFi mode; from the wizard's frequency/discovery step
   start a scan.
2. Confirm the plain ELRS device appears with the correct **kind** (TX/RX) and
   address (`10.0.0.1` for a self-AP, resolved IPv4 for mDNS).
3. Power the **Backpack** in WiFi mode; rescan. Confirm it appears as a
   **distinct** Backpack kind (`Backpack (TX)` / `Backpack (VRX)`).
4. **Non-leak check:** confirm the Backpack does **not** appear in the plain
   TX/RX list, and a plain ELRS device does **not** appear as a Backpack.
5. Select a discovered device and **probe** it. Confirm the identity card shows
   the device name / type / firmware (reachable), and that an **offline** device
   shows `reachable:false` (not an error).
6. If two devices resolve to the same address, confirm only **one** entry shows
   (dedup).

**Expected**

- Plain ELRS and Backpack devices are discovered on the right channel with the
  right kind; the M18/M19 boundary holds (no leakage either way).
- Probe of a live device returns its real identity; probe of an absent device
  degrades to `reachable:false` with no thrown error.
- mDNS prefers the IPv4 address; duplicates collapse to one device.

**Code under test**

- `src-tauri/src/commands/wifi.rs:436` `classify_ssid()` (M18, rejects
  Backpack/VRX), `:487` `classify_backpack_ssid()` (M19, accepts only Backpack),
  `:627` `parse_identity()` (HTTP identity), `:238` `probe_wifi_device()` (probe
  + SSRF guard).
- `src/lib/wifiDiscovery.ts`, `src/lib/backpack.ts` (the pure twins of the
  above), `src/components/wizard/StepFrequency.tsx`.

**HARDWARE-PENDING markers exercised**

- `src-tauri/src/commands/wifi.rs:320` — the serial-attached-Backpack pass is
  empty in dev (no attached Backpack); `:520` `detect_serial_backpack()` returns
  an empty list with no hardware. When a TX with an attached Backpack is
  present, confirm the Backpack surfaces here.

**Already proven (no device)**

- `tests/unit/wifiDiscovery.test.ts`, `tests/unit/backpack.test.ts` — SSID
  classify, mDNS→DTO, source labels, the non-leak invariant, and (M29)
  whole-word TX/RX role matching (rejects `TXT`/`RXD`/`TX1` noise).
- `commands/wifi.rs` `#[cfg(test)]` — classifiers, parsers, SSRF allow/deny,
  identity parse, and (M29) malformed-JSON marker fallback + mDNS
  collision/dedup + multi-IPv4 preference.

**Result:** ☐ PASS  ☐ FAIL  ☐ blocked (no WiFi-mode ELRS device / no Backpack)

## (d) Record → session browse → CSV export round-trip — M11

Confirms a recorded telemetry session (with a real GPS track) persists, lists in
the session browser, and exports to a canonical CSV that re-imports identically.

**Preconditions**

- A live ELRS link with telemetry (and, ideally, a GPS fix per section (a)) so a
  recording contains both link stats and GPS rows.
- OmniLink running under Tauri (SQLite persistence is Tauri-only).

**Steps**

1. With telemetry live, **start recording**; fly/move for a minute so the
   session contains a GPS track plus link-stat variation.
2. **Stop recording.** Open the session browser (Logs / SessionPicker).
3. Confirm the new session lists with a sensible duration, frame count, and
   device/target label.
4. **Export** the session to CSV. Open the file: confirm the header column order
   matches `TELEMETRY_CSV_COLUMNS`, that GPS columns hold real values where a fix
   existed and are **empty** where there was none, and that timestamps are
   integer ms.
5. **Re-import** the CSV (via the Simulator replay path, M16). Confirm it replays
   through the live dashboard widgets identically (a round-trip).
6. Rename and delete a session; confirm the browser reflects both, and that a
   deleted session removes its frames too.

**Expected**

- The session persists and lists correctly; duration/frame-count are right.
- Exported CSV is the canonical format; GPS `0,0` (acquiring) renders as `0`
  cells, real no-GPS rows render as **empty** cells, and both re-parse correctly.
- Export → re-import is lossless (replay matches the recording).

**Code under test**

- `src/lib/telemetry-session-csv.ts` (`telemetrySessionToCsv` /
  `parseTelemetrySessionCsv`, column order + null/empty/0 coercion).
- `src/lib/sessions-db.ts` (`dbRowToCsvRow`, `dbRowToSessionMeta`,
  `formatSessionDuration`, delete/rename/prune SQL).
- `src/components/logs/SessionPicker.tsx`.

**HARDWARE-PENDING markers exercised**

- None specific to CSV — but the GPS columns are only *real* once section (a)
  passes on hardware (a recording made without a GPS module has empty GPS cells
  by design). Cross-reference (a)'s markers for the GPS values' provenance.

**Already proven (no device)**

- `tests/unit/telemetrySessionCsv.test.ts` — header/column order, null→empty
  round-trip, validation, and (M29) GPS `0,0`-vs-empty-vs-null coercion, CRLF/LF
  tolerance, 13-digit ms + fractional precision.
- `tests/unit/sessionsDb.test.ts` — row mappers, duration formatting, retention
  policy, delete/rename SQL shape.
- `tests/unit/telemetrySessionWriter.test.ts` — the write seam.

> The CSV serializer does **not** implement RFC-4180 quoting (it is a plain
> `String(n)` comma-join over numeric-only columns); do not expect quoting, and
> the tests deliberately assert only the behavior the code implements.

**Result:** ☐ PASS  ☐ FAIL  ☐ blocked (no Tauri build / no live telemetry)

## Release / updater (M21 / M22) — published-release acceptance (DEFERRED)

The release pipeline and in-app updater are **already real** and are NOT altered
by M29:

- `.github/workflows/release.yml` is **tag-triggered** (`on: push: tags:
  ['v*']` + `workflow_dispatch`) and uploads installers + updater artifacts to a
  single draft GitHub Release.
- `src-tauri/tauri.conf.json` has `createUpdaterArtifacts: true`, a real
  `endpoints` entry
  (`https://github.com/AbdulrahmanHR/OmniLink/releases/latest/download/latest.json`)
  and a real base64 minisign `pubkey`.

Publishing a real signed Release and accepting the end-to-end auto-update on
real machines requires repo signing secrets + a published tag, which is **out of
scope here and DEFERRED**. To accept later: push a `vX.Y.Z` tag, review the draft
Release, publish it, then confirm an installed older build updates itself via
Settings → App Update.

**Result:** ☐ PASS  ☐ FAIL  ☑ deferred (no published Release / signing secrets)
